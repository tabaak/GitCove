# Milestone 0 results and decision record

All runs on 7 Nov 2026 against `gitcove-sandbox/cove-spike` (private, GitHub Team), with Apps `cove-ro-gitcove-sandbox` and `cove-rw-gitcove-sandbox`. Raw evidence is in `fixtures/<spike>/`. "Design change" names the section of `idea-v2.md` to update.

## Spikes

| Spike | Result | Design change |
|---|---|---|
| **A: ruleset visibility** | **Confirmed.** With Metadata: read only, `rules/branches/{b}` returns repo and **org** ruleset rules with `ruleset_source_type`, and omits disabled rulesets and classic protection. `protected` is true for classic protection and for any active ruleset, including linear-history-only; false for disabled ones. `rulesets?includes_parents=true` lists all rulesets, disabled included, with `enforcement`. `branches/{b}/protection` needs Administration: read and says "Branch not protected" for ruleset-only branches even to an admin. `orgs/{org}/rulesets` is 403 for the App | §6 Protected branches: protected = `protected` true OR rules non-empty. Store rule types. Never use the classic protection endpoint. No Administration permission needed |
| **W: workflow-file check** | **Refuted: the check is tree-based.** Without `workflows`, GitHub accepts a push only if the pushed tip's `.github/workflows` tree equals that of some existing branch tip. Rejected: a branch at an older `main` commit already on GitHub (case 3), and a new ordinary commit on that old base (case 4, the failover case). Accepted: a commit already at another branch's tip (5), new commits on top of another tip (10, 11), and case 4 again once a branch tip with the same workflow tree existed (12). REST `POST /git/refs` behaves the same. With Workflows: write, everything is accepted | §8.6 and the plan check: a failover branch fails only when **its workflow tree matches no current branch tip** on GitHub, i.e. a workflow file changed on GitHub after the developer branched, or the developer edited one. Plan check = compare the branch's workflow tree with every current tip. Default stays no `workflows` permission; such branches go to `conflicts` with the reason |
| **M: marker and listing lag** | **Confirmed, with a lag.** Marker is kept in raw `body`, absent from `body_html`. `creator=<slug>[bot]` works. Comment listing (`issues/{n}/comments?since=`) showed new comments on the first poll (~0.4–0.7 s). **Filtered issue listing lagged 2.6–5.1 s** after the `201`. All 3 writes whose client timed out (0.2–0.6 s) **were created**. Search found both markers within 1 s | §8.3/8.4 case 6: before declaring an issue unsent, wait at least 15 s and recheck twice; comments can use a shorter wait. Lost responses are real and common at short timeouts, so the marker check is essential |
| **I: inline comments** | **Confirmed.** A line comment or review with an older `commit_id` that is part of the PR is accepted and anchored to that commit; after the branch moves, GitHub shows it as **Outdated** with the original diff, and `line` becomes null (`original_line` kept). A `commit_id` that isn't part of the PR, whether never pushed or random, gets `422 "commit_id is not part of the pull request"` | §8.13 as written. Replay must push the commit first; if it's absent from the PR, fall back to an ordinary comment |
| **Fixes #N** | **Confirmed.** An App-created PR with "Fixes #8" closed issue 8 on merge (`state_reason: completed`, closed by the bot) | §8.7 linked issues: rely on GitHub's close; don't replay the close separately |
| **E: read-only sync, `refs/pull`, CI** | **Confirmed.** cove-ro (Metadata, Contents, Issues, PRs read; Members read) gets 200 on collaborators, org members, outside collaborators and teams. `repos/{r}/teams` needs Administration: read. `refs/pull/*` lists and fetches. Push is refused ("Write access to repository not granted"). An App-created PR triggered both `push` and `pull_request` runs, not `action_required`. (The failed `z2.yml` run is spike W's invalid stub, not a finding) | §9 permission sync can use collaborators directly. Replay pushes and PRs **will run CI**; the plan screen must say so |
| **U: acting as the person** | **Confirmed.** Device flow works (manual "Enable Device Flow" tick; manifests can't set it). User token: 8 h (`28800`); refresh token ~181 days (`15638400`); refresh rotates, and the old refresh token then fails (`bad_refresh_token`). Comments show the person with the App badge. An approval via the user token turns `reviewDecision` to APPROVED and the merge state to CLEAN. Pushing a commit with dismiss-stale on resets it. **An APPROVE with an older `commit_id` is refused** (422 "pull request has been updated since you started reviewing") | §8.12/8.13 viable, so D3 can be "yes". R7 is also enforced by GitHub, so when the head moved, replay posts the approval as a note. Store the newest refresh token atomically: a crash between refresh and save loses the authorisation |
| **R: content-write limit** | **Not tripped.** 521 content writes (1 issue, 520 comments) from cove-rw in 15 min 48 s, about 33 a minute with 1 s pauses, all `201`. Response headers show only the primary limit (`x-ratelimit-limit: 5000`, resource `core`); nothing reports the content-write budget. So the documented 500 an hour wasn't enforced at this count and pace on this date, and `Retry-After` behaviour stays unobserved | §8.9: keep the documented budget (60 a minute, 450 an hour), because GitHub states it and can enforce it at will. Keep the client-side write count, since no header shows it. The block path (stop the queue, wait for `Retry-After` or at least a minute) stays untested against GitHub, so `fakehub` must cover it |
| **App manifest flow** | **Works.** Org-owned private Apps created from a manifest; App names are global, so the org name was appended. The code arrives only as a redirect to `redirect_url`, so setup needs a short-lived local listener (used here) | §3 setup: `cove setup` runs a local callback listener and names the App `cove-<org>` |
